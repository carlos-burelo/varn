# UI layout v2: layout responsivo, claves estables y layout reactivo

Estado: aprobado (decisiones 1 a 4 abajo). Breaking changes permitidos (Ley 10).
Alcance: `std:ui` (vn) y `varn-ui` (nativo). No cambia el lenguaje ni `std:signals`, solo los consume.

## 0. Decisiones aprobadas

| # | Decisión | Elegida |
|---|---|---|
| 1 | Reconciliación | Claves obligatorias en `Each`; opcionales en el resto; sin clave, ruta de posición |
| 2 | Señales dentro de builders | Permitidas, con seguimiento: el layout es un `computed` de `std:signals` |
| 3 | Flex | Intrínsecos (min/max content) además de constraints |
| 4 | Breakpoints | `enum WindowClass` fijo; umbrales configurables en `Theme` |

## 1. Problema

Medido en el código actual (`std/ui/widget/flex.vn`, `box.vn`, `scroll.vn`):

- `paint` vuelve a llamar `measure` sobre los hijos. Cada nodo se mide una vez por cada ancestro: coste ~ nodos × profundidad.
- Los ids de controles salen de `nextSlot()`, que depende del orden de llamada. Si un nodo condicional cambia el número de hermanos, los ids posteriores cambian y se pierden foco, texto (`ownedEdit`) y offset de scroll (la clave de `vn-scroll` es el id).
- `run` reconstruye el árbol completo en cada frame, aunque solo cambie un número.
- Solo hay `maxW/maxH`. No hay `minW`, intrínsecos ni separación entre "cambiar parámetro" y "cambiar estructura".

Un layout adaptativo cambia la forma del árbol a menudo. Por eso el problema de ids y el de medición son el mismo problema.

## 2. Modelo

Cuatro capas, cada una con una sola responsabilidad:

1. **Descripción**: funciones que devuelven `Node`, valores inmutables. No miden ni pintan.
2. **Reconciliación**: el árbol retenido se actualiza contra la descripción por clave. El estado (foco, texto, scroll, animación) vive en el nodo retenido, no en un contador.
3. **Layout**: `layout(node, constraints) → Layout`, una pasada, memoizada por `(nodo, constraints)`. Produce rectángulos y tamaños.
4. **Salida**: pintura (comandos a `varn-ui`) y hit-test sobre el árbol de layout. Nunca vuelven a medir.

### 2.1 Constraints

```vn
class Constraints {
    minW: float; maxW: float;
    minH: float; maxH: float;
}
```

- `maxH` puede ser no acotado (`CONTENT_UNBOUNDED`, hoy 1e9). El sistema debe tratarlo como infinito, no como número grande.
- Un nodo recibe constraints y devuelve un `Size` dentro de ellas. Nunca decide su posición: la posición la fija el padre.

### 2.2 Intrínsecos (decisión 3)

Cada nodo expone dos consultas baratas, memoizadas:

- `minIntrinsic(axis)`: ancho/alto mínimo sin romper contenido.
- `maxIntrinsic(axis)`: tamaño natural sin restricción.

Flex reparte el espacio con esas dos magnitudes (fijos primero, luego `flex` proporcional, respetando min/max). Wrap las usa para decidir cortes de línea.

Sin intrínsecos, flex no puede distinguir "este hijo necesita 120 px" de "este hijo puede ocupar lo que sobre". Esa distinción es la que falta hoy.

### 2.3 Responsive (decisiones 1, 2 y 4)

```vn
enum WindowClass { compact, medium, expanded }

Responsive(
    build: (cls: WindowClass, c: Constraints): Node => match cls {
        compact => Column([sidebar(), content()]),
        medium => Row([sidebar(), Expanded(content())]),
        expanded => Row([sidebar(), Expanded(content()), aside()]),
    }
)
```

- `WindowClass` se obtiene de `c.maxW` con los umbrales de `Theme.breakpoints` (por defecto 600 y 840, como Material 3). `Theme` puede cambiarlos; `Responsive` no tiene umbrales propios.
- El builder corre **una vez por (nodo, clase)** durante el layout. Cambiar de tamaño sin cambiar de clase no reconstruye.
- `match` debe cubrir las tres clases o tener `default`. Ver Ley 7.
- Si el builder lee señales, la lectura queda registrada (decisión 2) y solo se relayouta el nodo afectado.

### 2.4 Valores adaptativos (separan parámetro de estructura)

```vn
Column(children, gap: Adaptive({ compact: 8.0, medium: 12.0, expanded: 16.0 }))
```

- Cambiar un `Adaptive` solo relayouta: no reconcilia hijos ni reconstruye. Hoy no hay esa distinción.
- `Adaptive` acepta cualquier tipo de propiedad (`float`, `int`, `bool`), no solo números.
- Clase faltante: se usa la clase más cercana por debajo. Si no hay ninguna, error de compilación cuando el tipo lo permita; si no, error en tiempo de construcción.

### 2.5 Environment

```vn
class Environment {
    width: float;
    height: float;
    theme: Theme;
    windowClass: WindowClass;
}
```

- Se pasa como parte del contexto de layout, no como signal global. Cada nodo que lo lee queda registrado como dependiente; un cambio de tamaño relayouta solo esos nodos.
- Por qué no signal global: haría que cualquier resize invalide widgets que no dependen del tamaño, y oculta la dependencia.

### 2.6 Claves (decisión 1)

- `Each(items, key: (item) => key, render)`: la clave es obligatoria. Sin clave, error en tiempo de construcción.
- Hijos sin clave: su identidad es la ruta de posición (índice de hermano dentro del padre) más el tipo de nodo. Válido para estructuras fijas.
- Un nodo cuyo tipo cambia en la misma posición se reemplaza y pierde su estado. Eso es esperado.
- `Responsive` no es una excepción: al cambiar de clase, sus hijos reconcilian por clave o por ruta dentro de la nueva rama. Los hermanos fuera de `Responsive` conservan su estado porque su ruta no cambia.
- Ids de controles nativos: derivados de la clave del nodo, no de `nextSlot`. `nextSlot` se elimina.

### 2.7 Layout reactivo (decisión 2)

- El layout de un nodo es un `computed` de `std:signals`. Sus dependencias son: constraints, `Environment` y las señales leídas por builders y propiedades.
- Una señal que cambia invalida solo los layouts que la leyeron. `run` deja de reconstruir el árbol en cada frame: solo reconstruye si cambia una señal que afecta a la descripción.
- El coste por frame pasa a ser proporcional a lo que cambió, no al tamaño de la app.

### 2.8 Hit-test y foco

- El hit-test recorre el árbol de layout (rectángulos ya calculados). Se acabó el "medir para saber dónde cayó el clic".
- El foco es un id de nodo (clave), no un entero de contador.

## 3. Lo que se borra

Según Ley 10, cada borrado declara ganancia, verificación y qué se elimina.

| Se borra | Ganancia | Verificación |
|---|---|---|
| `measure` llamado desde `paint` (`flex.vn`, `box.vn`, `scroll.vn`) | Una medición por nodo y frame; coste lineal | Contador de llamadas a `layout` en tests; bench de 1000 nodos antes/después |
| `nextSlot()` y ids por orden | Estado de foco, texto y scroll sobrevive a cambios de forma | Test: `Responsive` cambia de clase; un `Field` fuera de `Responsive` conserva texto y foco |
| Build completo por frame en `run` | Coste proporcional a lo que cambió | Contador de builds por frame: una señal no leída por la descripción no dispara builds |
| `Widget.measure/paint/fit` como protocolo | Un solo protocolo (`layout`) | Suite `tests/main.vn` completa en los 4 cuadrantes |
| `fr.clicked` por geometría repetida | Hit-test sobre el árbol de layout | Tests 215, 219, 246 |
| `maxW/maxH` como única restricción | Constraints completos | Tests de `minW`/`maxW` en flex y wrap |
| `Scroll` con `CONTENT_UNBOUNDED` ad hoc | `maxH` no acotado como concepto | Test: scroll dentro de `Responsive` con `maxH` infinito |

No se borra: el puente a egui para pintar y para controles. Sigue siendo el único camino de dibujo.

## 4. Etapas

Cada etapa termina con la suite completa en verde (`verify.ps1 -Fast`) y un commit por cambio coherente (Ley 9).

### Etapa 0: contrato y tests que fallan

- Tests `.vn` que describen el comportamiento deseado: layout a anchos fijos (320, 600, 900), estado preservado al cambiar de clase, contador de mediciones y de builds.
- Nada de código de producción todavía. Los tests quedan marcados como esperados-fallo hasta su etapa.
- Verificación: los tests existen y fallan por la razón correcta.

### Etapa 1: constraints y layout de una pasada

- `Constraints` con min/max y `maxH` no acotado.
- `layout(node, c)` para `Box`, `Column`, `Row`, `Text`, `Button`, `Spacer`, `Expanded`, en paralelo al protocolo viejo.
- Verificación: mismos rectángulos que el protocolo viejo en las pruebas actuales (232-ui-layout).
- Breaking: ninguno todavía; el viejo sigue.

### Etapa 2: reconciliación con claves y eliminación de `nextSlot`

- Árbol retenido, claves, `Each` con clave obligatoria.
- Ids nativos derivados de la clave.
- Verificación: test de conservación de foco y texto al reordenar un `Each`; test de scroll conservado.
- Breaking: `Each` sin clave deja de compilar; `nextSlot` desaparece.

### Etapa 3: `Responsive`, `Adaptive`, `WindowClass`, `Environment`

- Umbrales en `Theme.breakpoints`.
- Verificación: test que renderiza a 320/600/900 y compara comandos; test de contador de builds por clase.
- Breaking: ninguno de API previa; es aditivo hasta la etapa 6.

### Etapa 4: layout reactivo

- Layout como `computed`; `run` deja de reconstruir por frame.
- Verificación: contador de builds por frame; test de que una señal no leída no dispara builds.
- Breaking: `run` ya no reconstruye en cada frame; un builder que dependía de eso debe leer señales.

### Etapa 5: intrínsecos, flex nuevo y `Wrap`

- Intrínsecos min/max, flex con `flex` proporcional, `Wrap`, `minW`/`maxW` en `Box`.
- Verificación: tests de reparto de espacio y de cortes de línea de `Wrap` a varios anchos.

### Etapa 6: borrado

- Se borran `Widget.measure/paint/fit`, `nextSlot`, `fr.clicked` de los widgets (queda como primitiva si algún test lo usa), y el protocolo antiguo.
- Verificación: `grep` sin ocurrencias y suite completa.
- Actualizar `docs/UI-SPEC.md`.

## 5. Riesgos

- **Intrínsecos** son el mayor coste de implementación. Si la etapa 5 se alarga, se puede entregar flex con min/max y dejar intrínsecos para una etapa posterior, pero solo como plan explícito.
- **Invalidación**: si un hijo cambia su intrínseco, el padre debe relayoutar. Debe modelarse como dependencia del `computed`, no como caso especial.
- **Claves mal elegidas** por el usuario siguen siendo un problema. Los errores de clave duplicada deben ser explícitos.
- **Egui**: el layout no debe depender de egui para medir. El texto mide con `std:ui/text`, que ya está en la misma capa.

## 6. Preguntas abiertas

1. ¿`Wrap` expone su orden de cortes al usuario (`onLineBreak`) o solo pinta?
2. ¿Los intrínsecos son públicos (los puede consultar el usuario) o internos al layout?
